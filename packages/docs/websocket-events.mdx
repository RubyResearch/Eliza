---
title: "WebSocket events"
description: "Connect to the local elizaOS event stream and handle its versioned envelopes safely."
---

The agent HTTP server exposes a WebSocket endpoint at `/ws`. The dashboard uses
it for live status, runtime events, conversation updates, plugin progress, and
other UI notifications. Chat requests and streamed model responses use HTTP
and SSE routes; they are not sent through this socket.

## Connect

```typescript
const protocol = location.protocol === "https:" ? "wss:" : "ws:";
const socket = new WebSocket(`${protocol}//${location.host}/ws`);

socket.addEventListener("message", (event) => {
  const envelope = JSON.parse(event.data);
  handleEvent(envelope);
});
```

In local mode, a loopback connection may use the local trust boundary. Remote
connections require the same authentication policy as the agent API. Browser
clients cannot set an `Authorization` header during `new WebSocket()`, so use
the authenticated application client rather than inventing a query-token flow.

The server rejects upgrades for paths other than `/ws`, unauthenticated remote
connections, and payloads larger than its configured limit.

## Event envelopes

All messages are JSON objects with a `type` discriminator. Some replayable
events also carry stream identity, sequence, and timestamp fields. Narrow the
event by `type` before reading its payload:

```typescript
function handleEvent(event: StreamEventEnvelope) {
  switch (event.type) {
    case "status":
      updateStatus(event);
      break;
    case "agent_event":
      handleAgentEvent(event);
      break;
    case "conversation-updated":
      refreshConversation(event.conversation.id);
      break;
  }
}
```

The canonical client envelope types are exported through the UI API client in
`packages/ui/src/api/client-types-core.ts`. Server producers live in
`packages/agent/src/api/server.ts` and the focused route modules beside it.

## Client messages

The socket accepts a small set of control messages, including authentication
where required and active-conversation tracking used to target updates. Treat
all other server operations as HTTP API calls. The server validates inbound
frames before dispatch.

## Reconnection and replay

Connections can close during runtime restart, sleep, or network transitions.
Clients should reconnect with bounded backoff and resubscribe their local state.
Replayable envelopes include ordering metadata so a reconnecting client can
request or apply missed events without duplicating earlier ones.

Pass the highest applied `bufferSeq` as `lastEventId` (a bare integer or the
`evt-<n>` form) when reconnecting. The server keeps replay bounded. If retained
events cannot satisfy that cursor completely, it sends this control frame
before the partial event tail:

```typescript
type WebSocketReplayGap = {
  type: "replay-gap";
  version: 1;
  requestedAfter: number;
  availableFrom: number | null;
  availableThrough: number | null;
  replayedFrom: number | null;
  replayedThrough: number | null;
  reasons: Array<
    | "cursor-ahead"
    | "retention-gap"
    | "replay-limit"
    | "unsequenced-event"
  >;
};
```

Treat `replay-gap` as an explicit resync requirement. Fetch authoritative HTTP
state before treating the retained tail as complete. Unknown clients keep the
legacy bounded tail because the control frame is additive and ordinary event
envelopes are unchanged. A connection without a cursor still receives the
historical tail and makes no completeness claim.

Use the shared frontend API client when building inside this repository; it
already owns connection state, parsing, replay, and listener cleanup. Custom
clients should:

1. reject malformed JSON and unknown required fields;
2. ignore unknown event types for forward compatibility;
3. deduplicate replayed sequence numbers;
4. remove listeners and timers on shutdown;
5. fetch authoritative HTTP state after an unrecoverable replay gap.

The replay rules are implemented in
[`packages/agent/src/api/ws-event-replay.ts`](https://github.com/elizaOS/eliza/blob/develop/packages/agent/src/api/ws-event-replay.ts).

## SSE response streaming

Chat streaming uses Server-Sent Events on the HTTP chat route. Its frames
represent message and content-block lifecycle, deltas, completion, and errors.
Do not mix SSE frames with WebSocket event envelopes; they have separate
transports, ordering, and cancellation behavior.
